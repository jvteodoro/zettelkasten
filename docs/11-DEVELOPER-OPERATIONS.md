# Developer operations, Git hooks and CI

## Local prerequisites

- Java 21 JDK (LTS), Maven 3.9+, Git, POSIX shell for the provided hooks.
- Maven wrapper will be generated by implementation issue ZK-01 with wrapper JAR checksum/version pinning; until that issue the project has no Java source or pom.xml. Do not claim builds pass before source exists.
- CI uses the same \`mvn -B verify\` command. The tracked hook scripts are not automatically activated by cloning.

## Install hooks

~~~sh
bash scripts/install-git-hooks.sh
git config --local --get core.hooksPath
~~~

Expected result: \`.githooks\`. Hooks are POSIX shell scripts; file modes tracked as executable.

### pre-commit

- Validate staged filenames against accidental secrets/binary database/archive artifacts and merge-conflict markers.
- Reject trailing whitespace in staged Markdown/Java/YAML/JSON/SQL, except intentionally exempted generated fixtures.
- Reject obvious patch with \`TODO REMOVE\` / \`FIXME SECURITY\` markers; do not block normal TODO.
- Run \`git diff --cached --check\`.
- Does not modify the working tree; never auto-format unstaged changes.

### pre-push

- Runs \`mvn -B verify\` if pom.xml exists, otherwise prints a clear scaffold-pending notice and runs documentation/structure checks.
- If Maven is missing after a pom exists, fail with explicit instruction.
- May be skipped explicitly with \`SKIP_LONG_HOOKS=1\` for emergency debugging; CI remains mandatory; no silent bypass.

### CI

\`.github/workflows/ci.yml\` runs shell/structure gates on all pushes and PRs; when pom exists it also runs Maven verify with Temurin Java 21 and archives test reports on failure. Maven verify must be the complete gate in the finished project. Hook shell scripts validated with \`sh -n\` and Bash installer with \`bash -n\`.

## Commit conventions

- \`feat(domain): ...\`, \`feat(tui): ...\`, \`feat(storage): ...\`, \`test(...): ...\`, \`docs: ...\`, \`fix(...): ...\`.
- Each PR references the implementing issue \`Closes #NN\`, describes tests and manual reproduction, includes database compatibility note, screenshots/transcript for TUI and explicitly lists non-goals.
- Never commit user DB/backup, private research notes, Zotero local database, secrets, editor caches or terminal capture with personal content.

## PR review checklist

See \`.github/pull_request_template.md\`. Follow acceptance in each issue. For schema changes, reviewers verify migration rollback behavior and deterministic export; for UI changes verify no hidden shortcut. New dependencies require license and provenance review.

## Setup of branch controls (GitHub settings)

Owner should enable branch protection on main: PR required, CI status required, prevent force-push/delete, review before merge and linear history if preferred. GitHub App integration may not have repository settings permission; documentation is not a claim these rules were enabled.

## Tests & developer commands (targets after ZK-01)

~~~sh
mvn -B -DskipTests=false verify
mvn -B test
mvn -B -Dtest=AddressParserTest test
mvn -B -DskipTests package
java -jar target/zettelkasten.jar --help
~~~

Do not hardcode the jar name without configuring packaging. Post-install smoke tests should use a fresh temporary DB, not the developer's personal slipbox.
